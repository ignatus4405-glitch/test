# Nginx Proxy Manager: 3 ресурса на одном внешнем IP, каждый — на своём локальном

Инструкция для случая: есть **один белый (внешний) IP**, за ним в локальной сети несколько машин с разными
адресами, и нужно, чтобы каждый ресурс открывался снаружи по своему адресу, а внутри сети оставался на своём
локальном IP и порту.

Работает по схеме «обратный прокси»: Nginx Proxy Manager (далее NPM) — единственная машина, которая смотрит
в интернет, и он решает, куда отправить запрос.

---

## 1. Что получится

```
                         Интернет
                            │
              один внешний IP: 203.0.113.10
                            │
                   ┌────────▼─────────┐
                   │  Роутер/файрвол  │  проброс 80/tcp и 443/tcp
                   └────────┬─────────┘
                            │
                   ┌────────▼─────────────────┐
                   │  NPM (Docker)            │
                   │  192.168.1.5  :80 / :443 │
                   └───┬──────────┬───────────┘
                       │          │
        app1.example.com    app2.example.com    app3.example.com
                       │          │                  │
              ┌────────▼──┐  ┌────▼──────┐   ┌───────▼───┐
              │ 192.168.1.10│  │192.168.1.20│   │192.168.1.30│
              │   порт 8080 │  │  порт 3000 │   │  порт 80   │
              └─────────────┘  └────────────┘   └────────────┘
```

Ключевая идея: **все три имени указывают на один и тот же внешний IP**, а различает их NPM по заголовку
`Host` (для HTTP) и по имени в TLS (`SNI`, для HTTPS). Внешний порт у всех один — 443, но внутри NPM
обращается к трём разным локальным адресам.

Пример, который используется ниже (замените на свои значения):

| Имя снаружи | Локальный адрес | Порт | Что это |
|---|---|---|---|
| `app1.example.com` | `192.168.1.10` | 8080 | веб-приложение |
| `app2.example.com` | `192.168.1.20` | 3000 | панель/API |
| `app3.example.com` | `192.168.1.30` | 80 | NAS / админка |

## 2. Что нужно заранее

- **Домен**, которым вы управляете (например `example.com`). Нужны три имени — либо `app1.example.com`,
  `app2.example.com`, `app3.example.com`, либо три разных домена. Без доменов будет работать только вариант
  с разными портами (см. раздел 9).
- **Внешний IP**, статический или динамический. Если динамический — настройте DDNS (DuckDNS, Cloudflare,
  у регистратора и т. п.).
- **Машина под NPM** в локальной сети с постоянным адресом (например `192.168.1.5`), на ней Docker и
  Docker Compose, свободные порты **80, 443, 81**.
- Доступ к настройкам роутера, чтобы сделать проброс портов.
- Локальные ресурсы должны быть доступны с машины NPM по их IP и порту. Проверьте это сразу:

```bash
curl -I http://192.168.1.10:8080
curl -I http://192.168.1.20:3000
curl -I http://192.168.1.30:80
```

Если здесь ошибка — NPM не поможет, сначала разберитесь с сетью/файрволом на самих ресурсах.

## 3. Установка NPM

Создайте папку и файл `docker-compose.yml`:

```yaml
services:
  app:
    image: 'jc21/nginx-proxy-manager:latest'
    container_name: nginx-proxy-manager
    restart: unless-stopped
    ports:
      - '80:80'      # HTTP
      - '443:443'    # HTTPS
      - '81:81'      # админка, только для локальной сети!
    environment:
      - TZ=Europe/Amsterdam
      # - DISABLE_IPV6=true   # раскомментируйте, если IPv6 на хосте отключён
    volumes:
      - ./data:/data
      - ./letsencrypt:/etc/letsencrypt
```

```bash
docker compose up -d
docker compose logs -f      # дождитесь сообщения о запуске, затем Ctrl+C
```

Откройте `http://192.168.1.5:81` и войдите с учётными данными по умолчанию:

```
Email:    admin@example.com
Password: changeme
```

NPM сразу попросит сменить их — смените на нормальные и сохраните в менеджере паролей.

> Не выставляйте порт 81 в интернет. Админка должна быть доступна только из локальной сети (или через VPN).
> Если очень нужно снаружи — сделайте отдельный прокси-хост вида `npm.example.com` на `127.0.0.1:81`
> и закройте его Access List, но проще оставить локально.

## 4. DNS: три имени на один IP

У регистратора домена (или в Cloudflare) создайте записи:

| Тип | Имя | Значение | Proxy (Cloudflare) |
|---|---|---|---|
| A | `app1` | `203.0.113.10` | DNS only (на время настройки) |
| A | `app2` | `203.0.113.10` | DNS only |
| A | `app3` | `203.0.113.10` | DNS only |

Для динамического IP вместо A-записей используйте DDNS-клиент и `CNAME` на ваше DDNS-имя.
Если домен в Cloudflare и включён оранжевый «прокси» — Let's Encrypt-валидация через HTTP-01 может не
пройти; на время выпуска сертификата переключите на «DNS only».

Проверка (с любой машины вне вашей сети, например с телефона по мобильному интернету):

```bash
dig +short app1.example.com     # должен вернуть ваш внешний IP
dig +short app2.example.com
dig +short app3.example.com
```

## 5. Проброс портов на роутере

Все три ресурса используют **одни и те же** внешние порты, поэтому правил нужно всего два:

| Внешний порт | Протокол | Внутренний адрес | Внутренний порт |
|---|---|---|---|
| 80 | TCP | 192.168.1.5 | 80 |
| 443 | TCP | 192.168.1.5 | 443 |

Ничего больше пробрасывать не нужно — порты 8080/3000/80 локальных машин в интернет не смотрят.
Порт 81 не пробрасывайте.

Проверка снаружи (с мобильного интернета, не из домашней сети):

```bash
curl -I http://app1.example.com
```

На этом этапе нормально увидеть страницу-заглушку NPM или `404`/`502` — главное, что запрос доходит.

## 6. Создание трёх прокси-хостов

В NPM: **Hosts → Proxy Hosts → Add Proxy Host** (Сайты → Прокси-хосты → Добавить).

Для каждого ресурса заполняются одинаковые по смыслу поля, отличаются только значения.

### 6.1. Вкладка Details

| Поле | app1 | app2 | app3 |
|---|---|---|---|
| Domain Names | `app1.example.com` | `app2.example.com` | `app3.example.com` |
| Scheme | `http` | `http` | `http` |
| Forward Hostname / IP | `192.168.1.10` | `192.168.1.20` | `192.168.1.30` |
| Forward Port | `8080` | `3000` | `80` |
| Cache Assets | выкл. | выкл. | выкл. |
| Block Common Exploits | вкл. | вкл. | вкл. |
| Websockets Support | вкл., если приложению нужны WebSocket | вкл. | вкл. |
| Access List | по желанию (пароль/IP-фильтр) | | |

Пояснения:

- **Scheme** — как NPM будет обращаться к ресурсу *внутри* сети. У 95 % домашних сервисов это `http`,
  даже если снаружи вы хотите `https`. `https` ставьте только если сам сервис уже отдаёт TLS
  (тогда понадобится включить «SSL Verify» или отключить проверку самоподписанного сертификата).
- **Forward Hostname / IP** — именно локальный адрес. Можно указать имя хоста, но только если оно
  резолвится внутри контейнера NPM; надёжнее — IP.
- **Block Common Exploits** — блокирует известные попытки эксплуатации (SQL-инъекции и т. п.).
  Если какой-то сервис начал странно себя вести, попробуйте временно выключить.

Нажмите **Save** и повторите для второго и третьего ресурса. В списке должно появиться три записи.

### 6.2. Вкладка SSL (для каждого из трёх хостов)

1. **SSL Certificate** → `Request a new SSL Certificate`.
2. **Force SSL** — включить (редирект с http на https).
3. **HTTP/2 Support** — включить.
4. **HSTS Enabled** — включать только когда убедились, что HTTPS работает стабильно; HSTS браузер
   запоминает надолго, и «откатить» его на клиенте сложно.
5. **Email Address** — рабочий e-mail (уведомления об истечении сертификатов).
6. Поставьте галочку согласия с условиями Let's Encrypt и сохраните.

Сертификат выпускается по HTTP-01: Let's Encrypt стучится на `http://app1.example.com/.well-known/...`,
поэтому порт 80 должен быть доступен снаружи. Если сертификат не выпускается — сначала исправьте это,
потом возвращайтесь к остальным двум хостам (у Let's Encrypt есть лимиты на количество неудачных попыток).

## 7. Проверка

```bash
# 1. Все три имени живы и отдают сертификат на нужное имя
curl -I https://app1.example.com
curl -I https://app2.example.com
curl -I https://app3.example.com

# 2. Проверка конкретно с вашего внешнего IP, в обход DNS/кэша
curl -kI --resolve app1.example.com:443:203.0.113.10 https://app1.example.com

# 3. Какой сертификат реально отдаётся на SNI app2
openssl s_client -connect 203.0.113.10:443 -servername app2.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -dates

# 4. Проверка редиректа http -> https
curl -I http://app3.example.com
```

Если все три команды из п.1 отвечают `200/30x` и разным содержимым — задача решена.

## 8. Частые проблемы

| Симптом | Причина | Что делать |
|---|---|---|
| Открывается страница «Congratulations» NPM | Ни один прокси-хост не совпал по имени | Проверьте `dig`, опечатку в Domain Names, не включён ли Cloudflare-proxy с другим именем |
| `502 Bad Gateway` | NPM не может достучаться до ресурса | Проверьте IP:порт с машины NPM, файрвол на самом ресурсе, правильный ли порт |
| `504 Gateway Time-out` | Ресурс отвечает слишком долго / не отвечает | Файрвол дропает пакеты, сервис висит, неверный порт |
| `404` от самого приложения | Приложение ждёт другое имя/путь | Настройте `base_url`/`trusted domains` в приложении (частая история у Nextcloud, GitLab) |
| Ошибка сертификата | Не выпущен / истёк / не то имя | SSL Certificates → Renew, проверьте доступность порта 80 |
| `400 Bad Request` / «plain HTTP request was sent to HTTPS port» | Наоборот: Scheme=`https` у ресурса, который работает по http (или наоборот) | Исправьте Scheme |
| Бесконечный редирект | Force SSL + приложение само редиректит/не видит `X-Forwarded-Proto` | Включите в приложении доверие к прокси-заголовкам |
| WebSocket не работает | Не включён `Websockets Support` | Включите галочку |
| Снаружи работает, изнутри дома — нет | Нет hairpin NAT / NAT loopback на роутере | Локальный DNS-сервер или записи в `hosts`, чтобы имена резолвились в `192.168.1.5` |
| В логах приложения IP клиента — адрес NPM | Так и должно быть | NPM передаёт `X-Forwarded-For`; включите доверие к нему в приложении |

Полезные места для диагностики:

```bash
docker compose logs -f app                 # логи самого NPM
docker compose exec app tail -f /data/logs/fallback_access.log
docker compose exec app ls /data/nginx/proxy_host/   # сгенерированные конфиги nginx
```

## 9. Если домена нет или нельзя открыть 80/443

### Вариант А: разные внешние порты (Streams, без имён и без HTTPS от NPM)

Подходит, когда доменов нет вообще. NPM умеет проксировать «сырой» TCP/UDP: **Hosts → Streams →
Add Stream**.

| Incoming Port | Forward Host | Forward Port | TCP/UDP |
|---|---|---|---|
| 8081 | 192.168.1.10 | 8080 | TCP |
| 8082 | 192.168.1.20 | 3000 | TCP |
| 8083 | 192.168.1.30 | 80 | TCP |

Не забудьте опубликовать эти порты в `docker-compose.yml` (`- '8081:8081'` и т. д.) и пробросить их
на роутере. Адреса снаружи будут вида `http://203.0.113.10:8081`.

Ограничения: TLS-терминации и выбора по имени здесь нет (кроме варианта «TCP + SSL forwarding» с
самоподписанным сертификатом), плюс у Streams — один порт на запись.

### Вариант Б: один домен, разные пути (Custom Locations)

Если домен один, а сервисы не умеют жить в подкаталоге, это плохой путь, но иногда работает.
В прокси-хосте для `example.com` добавьте **Custom Locations**: `/app1` → `http://192.168.1.10:8080`,
`/app2` → `http://192.168.1.20:3000`. Многие приложения (Nextcloud, Gitea, Home Assistant) потребуют
отдельной настройки на своей стороне — подкаталог должен поддерживаться приложением.

### Вариант В: Cloudflare Tunnel

Если провайдер блокирует входящие 80/443 (или IP за NAT), NPM можно вообще не выставлять наружу:
поставьте `cloudflared` рядом с NPM и публикуйте сервисы через туннель. Внутри туннеля указывайте
`http://192.168.1.10:8080` и т. д., а NPM оставьте для локальной маршрутизации.

## 10. Гигиена и бэкап

- Порты 80/443 — единственное, что смотрит в интернет. Всё остальное (81, 8080, 3000, БД) — только LAN.
- На самих ресурсах в файрволе разрешайте входящие соединения **только с `192.168.1.5`** (адреса NPM),
  а не со всей сети и уж точно не из интернета.
- Access Lists (Lists → Access List) — быстрый способ закрыть сервис паролем или ограничить по IP/стране.
- Резервная копия — это два каталога и файл конфигурации:

```bash
tar czf npm-backup-$(date +%F).tar.gz data letsencrypt docker-compose.yml
```

Сертификаты Let's Encrypt продлеваются автоматически; следите, чтобы e-mail в настройках был рабочим,
иначе об истечении вы узнаете в браузере.

- Обновление:

```bash
docker compose pull && docker compose up -d
```

## 11. Чек-лист

- [ ] Три имени в DNS указывают на один внешний IP (`dig +short` подтверждает).
- [ ] Роутер пробрасывает 80/tcp и 443/tcp на машину с NPM; 81 наружу не проброшен.
- [ ] Локальные сервисы доступны с машины NPM по своим IP:портам.
- [ ] В NPM созданы три Proxy Host, у каждого свой Forward Hostname/IP и Forward Port.
- [ ] Для каждого хоста выпущен сертификат Let's Encrypt, включён Force SSL.
- [ ] `curl -I https://appN.example.com` для всех трёх отдаёт содержимое нужного сервиса.
- [ ] Пароль админки NPM сменён с `changeme`, бэкап `data` и `letsencrypt` снят.
